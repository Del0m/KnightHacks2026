# Design: Vision Camera frame-processor plugin for pose

**Issue:** #42 [AI-02] Vision Camera frame-processor plugin for pose
**Date:** 2026-10-10
**Status:** Implemented and owner-tested on the standalone branch; FE-01 integration pending
**Context:** `Architecture.md` §4, §4.1; `docs/pose/pose-result-contract.md`; AI-01 spec `2026-10-09-pose-coreml-benchmark-design.md`

## 1. Goal

A native plugin that runs the YOLOv8n-pose Core ML model on each camera frame inside the Expo dev build and returns 17 joints with confidence to JavaScript, at 15+ fps on a recent iPhone.

Acceptance criteria from the issue:
- Works in the Expo dev build
- Returns joints + confidence per frame
- 15+ fps on a recent iPhone

## 2. Decisions

| Topic | Decision |
|---|---|
| FE-01 was not done at implementation start | #42 creates a minimal `apps/mobile` Expo dev build: one debug screen, no navigation or theme. FE-01 is now on main; integration must preserve its navigation and theme. |
| Expo | SDK 57 (React Native 0.86), continuous native generation: `ios/` is generated by `expo prebuild` and gitignored |
| Camera library | `react-native-vision-camera` **v5** (Nitro-based). Architecture §4 says v4, but v4's last release was Nov 2025 and predates RN 0.86. |
| Plugin form | A local Nitro package, `apps/mobile/modules/steadyforum-pose/`, modelled on the official `react-native-vision-camera-barcode-scanner` v5 plugin |
| Shared Swift code | AI-01's `PoseCore` consumed as a local CocoaPod (`PoseCore.podspec` beside its `Package.swift`), included via `expo-build-properties` `ios.extraPods`. One tested copy of the decoder. |
| Model delivery | Bundled at build time. `export.py` (AI-01) produces the `.mlpackage` files; a config plugin adds them to the Xcode target at prebuild. Gitignored. |
| Model size | 320 px default, 256 px available (per `docs/pose/benchmark-results.md`) |
| Frame rate | Throttled to 15 fps in the worklet (`maxFps`, default 15) |
| Platforms | iOS only. Android/TFLite is out of scope. |
| Debug screen | Camera preview, SVG skeleton, fps / inference ms / person score readout, front/back toggle |

Each unit has one job:
- **`HybridPoseDetector`** is the only new code that touches Core ML. It loads `yolov8n-pose-<size>` through `ModelLocator` with compute units `.all`, runs a `VNCoreMLRequest` with `.scaleFit`, and decodes with the existing `PoseDecoder`.
- **`ImageOrientation`** (PoseCore) maps a frame's rotation and mirroring to a `CGImagePropertyOrientation` and the upright frame size. It is pure and tested on the Mac.
- **`usePoseOutput`** is the single entry point for AI-03, AI-04, AI-06 and FE-05.
- **The debug screen and skeleton** can be removed or replaced by FE-01/FE-05 without touching the plugin.

Deviations from the issue's "Where" (`apps/mobile/src/pose/`), to note in the PR:
- Native code lives in `apps/mobile/modules/steadyforum-pose/`, since a native package cannot live under `src/`.
- Additions to AI-01's PoseCore: the podspec, `ImageOrientation` and `FrameTimestamp`.

## 4. Native interface

`modules/steadyforum-pose/src/specs/PoseDetector.nitro.ts`:

```ts
import type { HybridObject } from 'react-native-nitro-modules'
import type { CameraFrameOutput, Frame } from 'react-native-vision-camera'

export interface Joint { x: number; y: number; c: number }

export interface PoseResult {
  source: string        // "coreml"
  model: string         // "yolov8n-pose-320"
  timestamp_ms: number  // Unix ms
  score: number         // person confidence 0–1
  joints: Joint[]       // always 17, COCO order
}

export interface PoseDetection {
  result?: PoseResult   // undefined when no person is found
  latencyMs: number
}

export interface PoseDetector extends HybridObject<{ ios: 'swift' }> {
  readonly model: string
  setFrameOutput(output: CameraFrameOutput): void
  detect(frame: Frame): PoseDetection
}

export interface PoseDetectorFactory extends HybridObject<{ ios: 'swift' }> {
  createPoseDetector(size: number): PoseDetector  // 320 or 256; anything else throws
}
```

Field names match `docs/pose/pose-result-contract.md` exactly, so a cloud result (CONN-11) parses to the same `PoseResult` type. No person found is `undefined`, never an empty `joints` array.

## 5. Data flow

1. Vision Camera delivers a `Frame` on its frame thread, in sensor orientation, with `orientation` and `isMirrored`.
2. In the worklet, `usePoseOutput` calls `shouldProcess(nowMs, lastMs, maxFps)`. If less than `1000 / maxFps` ms have passed since the last processed frame, it disposes the frame and returns.
3. `detector.detect(frame)` in Swift:
   - casts the frame to `NativeFrame` and takes its `CMSampleBuffer` / pixel buffer; throws if missing
   - uses the bound frame output's live capture connection and a detached reference connection to determine the camera-specific correction angle; the reference is not added to the session
   - calls `ImageOrientation.vision(captureRotationDegrees:bufferRotationDegrees:mirrored:width:height:)` to get the Vision orientation and the upright width and height
   - runs `VNImageRequestHandler(cvPixelBuffer:orientation:)` with the `.scaleFit` request
   - decodes with `PoseDecoder.decode(…, frameWidth: uprightW, frameHeight: uprightH, …)`
   - converts the sample-buffer capture time to Unix milliseconds through `FrameTimestamp`, using the host-clock offset
   - returns `PoseDetection` with latency measured from Vision handoff to decoded joints (same definition as the #41 benchmark)
4. The worklet disposes the frame and hands the `PoseDetection` to the JS thread with `scheduleOnRN` from `react-native-worklets`.
5. On the JS thread, the hook calls `onPose(detection)` and updates a rolling fps count of processed frames.

Hook signature:

```ts
const { frameOutput, fps, error } = usePoseOutput({ size: 320, maxFps: 15, onPose })
```

**Orientation and mirroring rule:** joints leave the plugin upright and unmirrored, with anatomical left and right, as the contract requires. The front-camera mirror is applied only when drawing, in `overlayGeometry.ts`.

Device follow-up: swapping the frame flag's quarter-turn names globally fixed the back camera but regressed the front camera on the owner's phone. The hook now binds the native frame output before callbacks start. The detector compares AVFoundation's target angle for the active camera with the live connection's existing rotation. It recalibrates on camera or target-orientation changes. This keeps interface orientation without physically rotating buffers or assuming a fixed sensor mounting.

**Model files:** `withPoseModels` copies `yolov8n-pose-320.mlpackage` and `yolov8n-pose-256.mlpackage` from `ml/pose_export/PoseBench/PoseBench/Models/` (where `export.py` writes them) into the generated iOS project and adds them to the app target's sources, so Xcode compiles them to `.mlmodelc` and `ModelLocator` finds them in the main bundle.

## 6. Errors

| Case | Behaviour |
|---|---|
| Model files missing at prebuild | `withPoseModels` fails with: run `uv run export.py` in `ml/pose_export` first |
| Model missing at runtime | `ModelLocator` throws → `createPoseDetector` rethrows → hook returns `error`; debug screen shows a banner |
| One frame fails | `detect` throws; the worklet catches it, counts it and reports the last message. The stream continues. |
| Unsupported size | `createPoseDetector` throws `unsupported size <n>; use 320 or 256` |
| Camera permission denied | Debug screen shows a message and an "Open Settings" button |

## 7. Testing

| Where | What |
|---|---|
| Mac, `swift test` in PoseCore | `ImageOrientationTests`: 4 rotations × mirrored on/off → expected Vision orientation and upright size. Existing PoseCore tests still pass. |
| Mac, Jest in `apps/mobile` | `overlayGeometry` (cover crop, front-camera mirror; same cases as the Swift tests), `throttle`, contract shape (17 joints, fields) |
| Mac, typecheck | `tsc --noEmit` over `apps/mobile`; Nitro codegen re-run shows no diff |
| iPhone, manual (checklist in the PR) | Front and back camera, portrait; raise left arm → left wrist joint moves; skeleton lines up with the body; ≥15 fps at 320 on iPhone 17 Pro Max (and an older phone if available); frame-drop count steady over 60 s |

## 10. Done when

- The debug screen runs in the Expo dev build on an iPhone and shows a skeleton that tracks the user.
- `onPose` receives a contract-shaped `PoseResult` (or `undefined`) per processed frame.
- The fps readout holds ≥15 at 320 px on a recent iPhone.
- `swift test`, Jest and `tsc` pass.
