# Design: YOLOv8n-pose on Core ML + PoseBench test app

**Issue:** #41 [AI-01] Export YOLOv8n-pose to Core ML and benchmark on iPhone
**Date:** 2026-10-09
**Status:** Approved in conversation, awaiting spec review
**Context:** `Architecture.md` §4, §4.1, §18

## 1. Goal

From a fresh clone, get YOLOv8n-pose running live on an iPhone in a few minutes: the camera feed with the 17 joints drawn on it, real latency and fps numbers, and a button that copies a ready-made row for the PR table.

## 2. Decisions

| Topic | Decision |
|---|---|
| What the phone shows | Live camera, skeleton overlay, latency/fps readout |
| App | Native SwiftUI, standalone, in `ml/pose_export/PoseBench/` |
| Xcode project | Generated by XcodeGen from `project.yml`; the generated `.xcodeproj` is committed too, so opening it needs no extra tools |
| Install | Free Apple ID, phone plugged into the Mac (7-day signing) |
| Devices | One phone (the issue owner's). The copy-row button lets others add rows later. |
| iOS target | iOS 17+ (all phones are iPhone 12 or newer) |
| Model variants | 320 px and 256 px, FP16 |
| Model delivery | Bundled at build time; `export.py` writes them into the app; gitignored |
| Inference path | Vision (`VNCoreMLRequest`) wrapping Core ML, compute units `.all` |
| People per frame | One. The most confident candidate wins, so no NMS. |
| Frame rate | Live view throttled to 15 fps (10–15 fps is enough for rep data) |
| Controls | Model size 320/256, camera front/back (default front) |
| Results | "Run benchmark" button, then "Copy row" with a markdown row for the PR |
| Python | uv, Python 3.11, dependencies locked in `uv.lock` |
| Docs | `docs/pose/`: shared knowledge for the team and Claude |

## 3. Non-iPhone users (constraint from outside this issue)

Android and older phones will send frames to a server (**CONN-11**, `ml/cloud_endpoint/`, Architecture §4.1). This issue does not build that server, but it defines the **pose result contract** (§6) that the on-device path and the server must both produce, so the rep rules downstream cannot tell which one the joints came from. `PoseDecoder`'s logic is written as a pure function and documented step by step so CONN-11 can mirror it in Python.

```
    │   ├── PoseResult.swift     # the contract (§6)
    │   ├── PoseDecoder.swift    # raw tensor → PoseResult, pure

    │   ├── CameraFeed.swift     # AVCaptureSession, front/back, 15 fps throttle
    │   ├── Benchmark.swift      # warm-up, measurement, stats, markdown row
    │   └── ContentView.swift    # preview, overlay, readout, toggles, buttons
    └── PoseBenchTests/

docs/pose/
├── how-it-works.md
├── pose-result-contract.md
└── benchmark-results.md
```

Each Swift file has one job:
- `PoseDecoder` has no camera, UI or Core ML imports and is unit-tested.
- `PoseEstimator` is the only file that touches Core ML.
- `CameraFeed` only delivers frames.
- `ContentView` only draws.
- `Benchmark` only collects timings and formats output.

## 5. Export (`export.py`)

1. Download `yolov8n-pose.pt` via Ultralytics.
2. For each `imgsz` in (320, 256): `model.export(format="coreml", imgsz=imgsz, half=True, nms=False)`.
3. Rename the outputs to `yolov8n-pose-320.mlpackage` and `yolov8n-pose-256.mlpackage`.
4. **Verify** each package with coremltools: the input is an image of `imgsz × imgsz`, the single output has shape `[1, 56, N]` where N = (imgsz/8)² + (imgsz/16)² + (imgsz/32)² (2100 at 320, 1344 at 256). Fail loudly otherwise.
5. Copy both into `PoseBench/PoseBench/Models/`, replacing old copies.

Run with `uv run export.py` from `ml/pose_export/`.

## 6. Pose result contract

Defined in `docs/pose/pose-result-contract.md` and mirrored in `PoseResult.swift`. JSON form:

```json
{
  "source": "coreml",
  "model": "yolov8n-pose-256",
  "timestamp_ms": 1739000000000,
  "score": 0.91,
  "joints": [ { "x": 0.52, "y": 0.18, "c": 0.97 }, "... 17 total" ]
}
```

- `joints` always has 17 entries, in COCO order: nose, left_eye, right_eye, left_ear, right_ear, left_shoulder, right_shoulder, left_elbow, right_elbow, left_wrist, right_wrist, left_hip, right_hip, left_knee, right_knee, left_ankle, right_ankle.
- `x`, `y` are normalized 0–1 relative to the **upright, unmirrored camera image**, origin top-left. Mirroring the front camera is a display concern only.
- `c` is per-joint confidence 0–1. `score` is the person-detection confidence 0–1.
- `source` is `"coreml"` (on-device) or `"cloud"` (CONN-11).
- No person found means no `PoseResult` (Swift `nil`, JSON `null`), never an empty joints array.

## 7. Data flow

```
Camera (30 fps) → throttle (≥ 1/15 s since last accepted frame, else drop)
  → PoseEstimator: Vision resizes with .scaleFit (centered padding) → Core ML
  → raw [1, 56, N]
  → PoseDecoder → PoseResult?
  → ContentView draws joints + bones, readout
```

**Decode** (raw output, per candidate column i of N):
- Rows 0–3: box cx, cy, w, h in input pixels. Row 4: person confidence, already 0–1.
- Rows 5–55: 17 × (x, y, visibility), x/y in input pixels, visibility already 0–1.

Steps:
1. Pick the i with the highest row-4 value.
2. If it is below 0.25, return nil.
3. Undo the centered padding using the camera frame's aspect ratio and divide by the content size to get 0–1 coordinates.
4. Build a `PoseResult`.

`export.py`'s verification also asserts row 4 and the visibility rows fall within 0–1 on a sample image, so a layout change is caught at export time.

**Orientation:** the app is locked to portrait.
- Back camera: Vision gets `.right`.
- Front camera: Vision gets `.leftMirrored`, so the result is in unmirrored image space (§6). The overlay is then mirrored horizontally to line up with the mirrored preview.

**Readout:** model size · latency ms · effective fps · "no person" when no result.

## 8. Benchmark

"Run benchmark":
1. Show "Point at a person".
2. For each size, 320 then 256:
   - 2 s warm-up, discarded.
   - 10 s measurement with the 15 fps throttle **off**, counting only frames where a person was found. The timer pauses while no one is in frame.
3. Per size, record:
   - mean and p95 latency
   - max fps = 1000 / mean latency
   - holds 15 fps = p95 < 66.7 ms
4. Enable "Copy row", which puts one markdown row per size on the clipboard:

```
| iPhone 13 | iOS 26.1 | 256 | 6.2 | 8.9 | 161 | ✅ |
```

The columns are phone model, iOS version, size, mean ms, p95 ms, max fps, holds 15 fps.

**Latency** is measured from handing the frame to Vision until the decoded `PoseResult` returns. That covers resize, model and decode, the real per-frame cost.

## 9. Errors

| Problem | Behaviour |
|---|---|
| Camera permission denied | Full-screen message plus a button that opens Settings |
| Model missing from bundle | On-screen "Run `uv run export.py` first"; that size's toggle is disabled; no crash |
| Model fails to load | Core ML error text shown on screen |
| No person | Skeleton hidden, readout says "no person", benchmark timer paused |
| App backgrounded mid-benchmark | Benchmark cancelled; screen asks to run it again |

## 10. Testing

- **`PoseDecoderTests`** (no phone needed):
  - picks the most confident candidate
  - undoes padding for portrait and landscape frames
  - returns nil below threshold
  - always returns 17 joints in COCO order
- **`BenchmarkTests`:** mean, p95, max fps, the 15 fps flag and row formatting from a fixed list of timings.
- **Export verification:** shape and value-range checks in `export.py` (§5).
- **Manual on the phone:**
  - skeleton follows the body on both cameras, with left and right correct on the front camera
  - the size toggle switches models
  - a benchmark run produces copyable rows
